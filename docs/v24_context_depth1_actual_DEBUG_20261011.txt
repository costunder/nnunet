GPU6 context 간 깊이 >1mm 적용 — 실제 DEBUG 검증 보고서
기준일: 2026-10-11, Asia/Seoul
실제 CUDA 판정: 최초 first-B4 실행은 입력 provenance 오류로 실패.
수정 후 CPU 통합 검사는 통과했으나 CUDA 재실행은 할당 시간 부족으로 미실시.

현재 판정
사용자가 요청한 변경은 context의 간 깊이 조건만 >4mm에서 >1mm로
바꾸는 것이다. 별도 GPU6 first-B4 DEBUG에 적용했다. 실제 병변 4개의
source context 생성은 확인했다. CUDA 점수 계산 성공, 전체642개
채점 완료, nnU-Net 학습 또는 평가 완료를 주장하지 않는다.

정확한 입력 정의
- 변경 전 context: 간 조직 AND 종양 footprint 밖 AND 종양 거리
  2mm 이상/10mm 이하 AND 실제 간 경계까지 깊이 >4mm.
- 이번 context: 같은 조건에서 간 깊이만 엄격히 >1mm.
- 간 깊이 정확히 1mm인 복셀은 포함하지 않는다.
- 종양 거리의 하한은 기존 2mm를 유지했다. 사용자가 언급한 종양 거리
  1mm는 이번 적용 범위에 포함하지 않았다.
- 전체 종양 footprint와 10mm ROI margin, dense view 5x48x48x48,
  원래 canonical grid, graph sampling, edge 규칙과 CT 처리를 유지했다.
- 간 surface 역할은 기존 0<간 깊이<=3mm를 유지한다.
- 따라서 1<깊이<=3mm인 실제 조직은 context와 surface semantic mask에
  함께 들어갈 수 있다. 각 역할의 원래 grid를 적용해 서로 다른 typed
  node로 사용한다. 서로 다른 grid 간격 때문에 두 역할의 모든 canonical
  좌표가 항상 같다는 뜻은 아니다. 가짜 좌표나 대체 조직을 추가하지 않는다.
- Source context는 계속 필수다. 빈 source context를 기존 토큰으로
  통과시키는 앞선 제안은 이번 구현에 설치하지 않았다.
- 기존 target-only context absence 정책은 새 >1mm semantic mask를
  재검사하고 실제 surface가 남아 있을 때만 인정한다.

기존 실패와 실제 source 준비의 현재 확인 범위
기존 >4mm 조건에서는 liver_46/component001의 종양 거리 2..10mm 안에
조건을 만족하는 context 복셀이 0개여서 모델 forward 이전에 거부됐다.
전체 raw organ depth를 사용한 실제 마스크 검사로 확인된 실패이며,
CT 누락이나 ROI에서 종양이 잘려 나간 문제가 아니었다.

이번 실제 DEBUG의 CPU source 준비 로그에서 현재 확인한 값:
- liver_46/component001: >1mm context 실제 복셀 1,007개,
  canonical source_context node 168개. 기존 >4mm의 context 복셀은 0개.
- liver_117/component002: canonical source_context node 641개.
- liver_108/component001: canonical source_context node 444개.
- liver_93/component002: 실제 context 복셀23,164개,
  canonical source_context node774개.

위 값은 실제 source의 CPU geometry 준비 결과다. 이 결과만으로 실제
CUDA forward나 후보 점수 계산이 완료됐다고 해석하지 않는다.

검증 절차와 실제 실행 규모
- CPU UNIT 검사 5개 통과: strict >1mm 경계, 2..10mm annulus 보존,
  실제 원본 builder/sampling 및 공식 STU encoder 경로, 잘못된 geometry
  또는 기존 profile source 입력 거부를 포함한다.
- 기존 regression 검사 33개 통과.
- 원본 소스 활성화 import-order bootstrap 검사 1개 통과.
- 실제 실행에서 sampling wrapper closure가 원래 provenance 순회에
  인식되지 않는 오류가 발견됐다. 기존 검증을 완화하지 않고 새
  wrapper의 원본 호출 경로를 기존 bounded_view closure로 연결했다.
  v24_input_runtime.py는 변경하지 않았다.
- 수정 후 CPU UNIT5개를 다시 실행해 통과했다(8.289초).
  실제 _sampling_proof/_sampler/_materialize_pair를 포함하며, 원래
  materialization과 두 graph view의 노드/엣지/CT가 정확히 일치한다.
  외부 wrapper를 거부하는 부정 검사도 유지했다.
- 위 CPU 검사들은 실제 환자 CUDA 채점 또는 전체 학습 완료가 아니다.
- 실제 DEBUG는 기존 첫 번째 disjoint source B4를 사용한다.
  liver_117/c2, liver_108/c1, liver_46/c1, liver_93/c2.
- 각 source의 원래 모든 observed P와 원래 Basic CP 후보 128개를
  함께 처리하도록 요청했다. 기대 CP 점수 수는4x128=512개지만 첫
  local chunk materialization에서 오류가 발생해 실제 점수는 생성되지 않았다.
- 원래 source 전체 계약은 81명/642개 source/각128개 후보,
  총82,176개 위치다. 이번 DEBUG는 명시적인 4-source 실행이며 전체
  642개 검증 결과로 사용하지 않는다.
- Physical patient batch 4, physical candidate chunk 64, CPU worker 4.
- GPU6의 원래 measured candidate chunk 64와 전체 모델을 유지한다.
  DEBUG에는 optimizer update가 없으므로 gradient accumulation과
  effective optimizer batch는 해당 없음이다.
- 실제 STU forward 직전에 profile/10mm scope/역할별 canonical 및
  sampled node 수/target absence/eval-no-grad 조건을 검사한다.
- 완료 판정은 4개 source 모두 128개 유한 점수, 모든 P 유지,
  원래 BEST model state와 RNG 불변, 원본 source provenance 불변을
