# GNN·CP 공통 진행 화면 계약

Notion 재사용 기준: https://app.notion.com/p/3eabea17210b81c8969dd61f2aef459e 의 '공통 진행 화면 디자인 — UI schema 2' 절.
다음 진행 화면 작업은 이 계약과 Notion 양식을 먼저 읽고 기존 공통 renderer/adapter를 재사용한다. v2.5 등 새 실험 버전 때문에 화면을 새로 만들지 않는다.

UI schema version: 2 (작업 종류별 고정 디자인)
상태: GNN·CP 타입별 공통 화면 구현 및 Windows CPU 98개 검사 완료. 실제 서버 Linux CPU 98개 검사 및 GPU4·5·6 화면/기존 명령 재연결 검증 완료.

## 적용 범위

GNN 학습이면 실험 버전·encoder·curriculum과 무관하게 같은 GNN 화면을 사용한다. CP 후보 채점이면 같은 CP 채점 화면을 사용한다. nnU-Net의 기존 timestamp / Epoch / learning rate / OnlineCP / train_loss / val_loss / Pseudo dice / Epoch time 콘솔 형식과 학습 logger는 변경하지 않는다.

공통 렌더러 tools/training_monitor_ui.py, 입력 변환 tools/training_monitor_adapter.py를 사용한다. 새 실험은 로그 adapter와 과학적 버전 값만 연결한다. 버전별 renderer나 별도 표시 행을 만들지 않는다. 사용자가 요청한 UI 변경이 있는 경우에만 디자인 계약 버전을 올린다.

모든 단계를 한 화면에 넣었던 16행 UI schema1은 현재 표시 계약으로 채택하지 않는다. 기존 immutable release의 호출 호환 API만 보존한다. 현재 진입점은 render_task / TerminalView(layout='task')이다.

## GNN 고정 9행

1. GPU / GNN 학습 / 실험 버전 / UI 버전 / 실제 상태 / 읽기 상태
2. 현재·목표 epoch, 완료 epoch, active U, 실제 optimizer update, 완료 증거
3. 현재 학습 또는 validation phase, 완료 진행량과 progress bar
4. 최근 관측 train loss와 측정 update
5. 최근 완료 stage validation의 epoch / 평가 U / per-P MRR / top1
6. 최근 완료 full validation의 epoch / 평가 U / per-P MRR / top1
7. RSS, RAM 한도, 측정 범위와 프로세스 상태
8. 실제 후속 controller 상태, 단계와 대기 사유
9. 읽기 경고, 오래된 snapshot 표시와 실제 오류

## CP 고정 8행

1. GPU / CP 후보 채점 / 실험 버전 / UI 버전 / 실제 상태 / 읽기 상태
2. 완료 source / 전체 source, progress bar와 채점 상태
3. 완료 후보 위치 / 전체 후보 위치, progress bar
4. 자기 GPU의 GNN BEST 입력 또는 pin 검증 전 입력 계획
5. RSS, 실제 측정 범위와 프로세스 상태
6. 최근 실제 batch 시간, console 갱신 후 경과 시간
7. 실제 후속 controller 상태, 단계와 대기 사유
8. 읽기 경고, 오래된 snapshot 표시와 실제 오류

같은 작업 종류는 항상 같은 행 순서·항목·표기법을 유지한다. 아직 관측되지 않은 값은 행을 제거하거나 0으로 바꾸지 않고 '-'로 표시한다. 실제 기록의 0은 0으로 표시한다. TTY는 같은 위치를 갱신하고 Unicode 폭에 맞춰 긴 행을 자른다. --once에서는 전체 오류 경로와 원인을 볼 수 있다.

## 상태와 출처

상단 상태는 pipeline의 최신 읽기 상태를 우선한다. READ_PENDING / READ_ERROR가 발생했을 때 과거 nested RUNNING을 정상 상태로 보여주지 않는다. 최근 정상 값은 유지하되 '새 기록이 아님'을 표시하고 같은 파일을 재시도한다.

stage/full validation의 epoch와 평가 U를 각각 기록한다. 현재 U가 증가해도 과거 full validation의 평가 U를 바꾸지 않는다. GNN 완료, CP 채점 완료, nnU-Net 전체 학습 완료와 자기 BEST 전체 validation 완료는 독립적인 증거로 판단한다. 파일 존재나 source 진행률만으로 전체 파이프라인 완료를 주장하지 않는다. pseudo Dice는 BEST 전체 평가 성능이 아니다.

RAM은 현재 프로세스 트리, 현재 채점 PID, 과거 train update 측정을 구분한다. console 나이는 console 파일 mtime 이후 경과 시간이며 batch 완료 시각이나 정체 확정 시간이 아니다. snapshot_fresh는 이번 파일 읽기 성공 여부이다. 프로세스 sleeping만으로 작업 중단을 판단하지 않는다.

CP 화면의 후속 대기 사유는 실제 request/registration/status로 검증된 현재 controller 사유 하나만 사용한다. 과거 scoring request에 저장된 오래된 quota / 12.51GiB / 26.71GiB / controller 미등록 문구를 중복 표시하지 않는다. 새 controller가 없으면 실제 미등록 상태를 명시한다.

## 안전 경계 및 검증

화면은 관찰 도구이며 학습 시작·재시작, CUDA model load, 프로세스 신호, 학습 데이터·checkpoint·결과 쓰기를 하지 않는다. 실행 중인 과학 코드와 봉인된 module은 수정하지 않는다. 이전에 이 작업에서 생성한 display-only 진입점은 정확한 UID/regular-file/SHA 검사와 원본 백업 후 새 공통 뷰어로 연결한다. GPU1의 nnU-Net 학습 및 기존 콘솔 logger는 대상에서 제외한다.

Windows CPU 98개 검사 PASS: 작업 종류별 버전 간 고정 디자인, 미기록·실제0, phase progress, epoch/U provenance, 읽기 오류와 stale, Unicode/TTY/크기 변경/9→8행 전환/커서 복구, 기존 검증 경로, wrapper 설치. UI 검사 성공은 전체 학습 또는 전체 평가 성공을 의미하지 않는다.

실제 명령은 view_training.py --gpu 4|5|6이며 기존 view_gpu4_current.py / view_gpu5.py / view_gpu6.py 및 auto/current 별칭도 같은 공통 진입점에 연결한다. 이미 켜진 옛 뷰어는 학습을 유지한 채 뷰어만 Ctrl+C로 닫고 같은 명령을 다시 실행한다.
