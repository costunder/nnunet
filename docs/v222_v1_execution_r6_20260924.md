# v2.22 r6 실행 복구

기존 실행은 epoch 끝에만 checkpoint를 만들었다. PID27840을 명령·생성 시각으로 확인하고 사용자에게 보고한 뒤 단일 worker만 중단했다. 마지막 로그는 epoch1 step49, 2,389개 query였고 저장된 학습 가중치는 없었다. 원본 CT, 14,102개 완성 그래프와 기존 로그는 보존했다.

## 변경 범위

- `LocalBatch.to`: tensor clone 대신 PyG store shallow copy. CPU tensor의 pinned memory를 유지하며 CPU graph 자체의 device를 변경하지 않는다.
- `v1_execution.py`: optimizer 한 batch마다 `checkpoint_latest.pt`를 원자적으로 교체한다. 완전한 임시 파일을 fsync한 뒤 replace하므로 쓰기 실패 시 이전 checkpoint가 남는다. 새 run이 직접 만든 rolling 파일만 교체한다.
- 저장 항목: model/optimizer, Torch CPU/CUDA·NumPy·Python RNG, epoch/다음 batch/global step, 방문 query, partial loss, epoch support embedding, 현재 recipient group 및 이미 적합한 L2 plan. 중간 재개 시 L2 teacher를 새 가중치로 다시 적합하지 않는다.
- support encoding도 batch별 prefix를 저장한다. 초기 준비 및 epoch 후 memory refresh 도중 중단돼도 완료한 prefix를 다시 계산하지 않는다. validation 도중 중단하면 완료된 optimizer 상태에서 validation을 재실행한다.
- `STOP_AFTER_BATCH` 파일이 run 디렉터리에 생기면 현재 batch를 마치고 저장 후 정상 반환한다. 외부 세션·다른 프로세스를 종료하지 않는다.
- `run_v222_v1_l0.py train --resume <checkpoint> --cache <동일 index> --output <새 run>`으로 이어간다. source/config/cache identity가 다른 재개는 거부한다. allocator 정책도 일치해야 한다.

## 보존한 실험 계약

5,550,806 parameters, L0 3층/128D/4heads, L1 2층, L2 2층, CNN12/24/32, CT48³, 전체 train11,279·inner-val2,823, physical/effective64, accumulation1, worker8, GNN40epochs/9,360steps, seed42, CP80% 그대로다. 모든 node/edge와 관측을 보존한다. nnU-Net과 native online bank는 아직 별도 미완료다.

기존 cache를 새 형식으로 재생성하지 않는다. 실행용 새 index는 원본 metadata를 보존하고 execution source hash와 변경 감사만 추가한다. 원래 graph root와 record SHA 검증을 유지한다. 로컬 encoder 소스 AST는 전송 메서드와 copy import를 제외하면 같고, sampling/calibration/evaluation helper AST도 같다. 원본 v1 SHA 검증은 통과했다.

## 측정 및 검증 상태

- 단위/회귀20개 통과. checkpoint 쓰기 실패 시 이전 파일 유지, 성공 시 원자적 교체, CPU graph store 보존 포함.
- 실제 CT profile: `work/v222_v1_profile_r6_default_20260924/steps.jsonl`. full-size query batch64, support는 기존 실제 CT6개 DEBUG fixture. segmentation 성능 결과가 아니다.
- H2D 약0.03~0.04초, 전송 복사 제거만으로 전체 성능 문제 해결을 주장할 수 없다. 주요 시간은 forward/backward. reserved가11.9→14.4→16.9GB로 증가한 뒤 약40초대 batch가186초로 감속했다.
- 이 default profile 일부는 짧은 CUDA 단위검사와 겹쳤다. 독점 GPU A/B로 과장하지 않는다. 후속 release-unused 비교는 GPU 작업을 분리해 실행한다.
- 실제 checkpoint 재개 검증 통과: `work/v222_v1_resume_check_20260924_r6/result.json`. 연속 실행과 저장 후 재개의 loss·전체5,550,806 parameter·optimizer state가 비트 단위로 같았다. support prefix 재개도 비트 단위로 같다. 저장67,256,647bytes, 약0.37초. 최종 평가 callback까지의 재검증은 `work/v222_v1_resume_check_20260924_r6_final/result.json`에 기록한다.
- 실행기 전체 smoke 통과: `work/v222_v1_lifecycle_smoke_20260924_r6/result.json`. 실제 CT6개와 전체 모델로 step1 저장·정상 중단→새 run step2부터 재개→epoch 전체 방문→support refresh→validation→best checkpoint 마감까지 실행했다. 명시적 DEBUG에서만1epoch/6개 fixture를 사용하며 생산 설정40epoch/14,102개를 바꾸지 않았다. 이 smoke는 학습/검증 fixture가 같아 성능 평가로 사용할 수 없다. 모든 checkpoint에 debug=true를 기록하고 production resume는 거부한다.

## 성능 비교 완료

동일10개 batch 순서에서 query 수·node·edge·loss가 모두 정확히 같다. 사용하지 않는 allocator cache만 매 batch 반환한다. 모델이나 그래프 규모는 바꾸지 않았다.

| 측정 | 기본 allocator | batch 사이 unused cache 반환 |
|---|---:|---:|
| 10번째 batch (64 graphs, 46,852,381 edges) | 277.81초 | 48.00초 |
| 해당 batch reserved | 21.39GB | 12.77GB |
| 10개 batch 합계 | 759.14초 | 421.04초 |

근거: `work/v222_v1_execution_comparison_20260924.json`. 마지막 batch 개선5.79배를 전체 epoch 개선율로 일반화하지 않는다. 전체10개 합계 개선은1.80배이며 전체 cohort/epoch 시간은 별도 실측한다. 기본 profile의 짧은 별도 CUDA 검사 중첩 한계도 보존했다. 연속 batch cache 반환을 새 실행기의 기본값으로 적용했고 support·학습·평가 모두 같은 정책을 사용한다.

## 전체 실행

후속 전체 실행 경로는 `work/v222_v1_resumable_training_20260924_r6`이다. 실제 시작 여부와 현재 phase는 같은 이름의 `.status.json`, `checkpoint_status.json`, `first_optimizer_step.json`으로 확인한다. support 계산을 optimizer 학습 시작으로 표시하지 않는다. 원래49step의 미저장 가중치는 복구되지 않으므로 초기 가중치에서 다시 시작한다. 완성한14,102 graph는 `index_execution_r6_final.json`으로 재사용한다.

19:06:50 실제 확인: worker32276, supervisor6176, initial_memory128/11,279 완료. `checkpoint_latest.pt`22,492,537bytes와 원자적 저장 receipt 확인, 저장0.104초, stderr 없음. optimizer step0으로 아직 support 준비 단계다. 고정 시각 스냅샷이며 이후 상태는 live 파일로 확인한다. 소스 및 검증 아카이브: `versions/v2.22/v1_execution_r6_20260924/source.zip`.

## 작업 완료 체크리스트

최신 실행 방향: 사용자의 로컬 검증·A6000 서버 본학습 제안에 따라 로컬 run에 STOP_AFTER_BATCH를 요청하고 정상 중단을 확인했다. 저장된 support prefix는 보존했고 optimizer step0이다. 서버 학습은 아직 시작하지 않았다. 수정 후 local ETA는 optimizer153분 + memory refresh46.5분 + validation 추정최소11.6분 ≈3시간32분/epoch, 대략3.5~4시간이다. 최초support약47분 별도이며40epoch 약6~7일(GNN만). full epoch 실측값이 아니라 benchmark 및 초기production 처리량을 이용한 추정이다.
