# v2.2 LocalCNN / 10mm / cumulative U16 experiment

## Purpose and scope

The user authorized a new native v2.2 experiment: start each patient's query
training with all observed P and sixteen existing U, then add sixteen U only
after the cumulative training set passes a stage gate. Previously introduced U
remain active. This tests optimization under progressive query exposure; it
does not prove that candidate count is the cause of previous weak ranking.

This uses the existing **LocalCNN L0**, not crossed D's archived v1 GAT L0.
The local input is native-spacing, liver-masked CT with a **10mm margin on each
face outside the donor tumor bounding box**. No graph/partition preparation is
introduced. L0 keeps channels 12/24/32, convolutions 2/3/3, 128D output and the
existing multiscale masked readout/fusion. L1/L2 remain two layers, 128D, four
heads. The seed42 initialization, FP32/AdamW/constant LR, ranking softplus,
balanced observation CE and alignment objectives remain unchanged.

P means an observed eligible tumor anchor. U means an unobserved comparison
location. Neither label is redefined as donor-specific CP suitability.

## Curriculum contract

- Each patient's existing 128 U are ordered once by seed42 geometry/identity
  hash. No model score, annotation class within U, edge count or validation
  result selects the initial sixteen. Hash ordering avoids using an edge-cost
  prefix; it does not guarantee anatomical spatial coverage.
- All P stay active at every stage. All training patients, including zero-P
  cases, remain present. Zero-P cases receive their existing observation and
  alignment objectives; they cannot contribute a P/U ranking gate.
- Cumulative query stages are 16,32,48,64,80,96,112,128 U per case. Every active
  P×U pair is compared exactly once per epoch in live disjoint batches.
- Full row IDs and indices remain unchanged. Active pair counts, class counts,
  presentation multiplicity and optimizer-step normalization are recomputed at
  each stage. No detached positive reference is substituted for live ranking.
- The existing full observation memory and sixteen-patient support episodes
  remain unchanged. Deferred query U still exist in the full support bank.
  Therefore this experiment does not fix or isolate support-class imbalance.
- Physical batch remains32 in the production launcher. Early stages may have
  natural partial batches when a case contains fewer than32 active rows;
  sixteen U is not a change to the physical-batch setting. No fake padding
  observations are added to fill a batch.

The initial90% pair-win/Hit@1 proposal was lowered after the user questioned its
strictness. The reviewed default is now:

```
cumulative TRAIN P/U pair-win >= 0.70
case mean [max(score(P)) - max(score(active U))] > 0
both conditions hold for two consecutive completed epochs at the same stage
```

Hit@1 is still measured but has no minimum gate: required_hit_at_1=0. These are
explicit experiment thresholds, not validated optimal values. Their values are
stored in config/v22_cumulative_u16.json and copied into the experiment and
checkpoint identities. Changing a threshold requires a distinct experiment.

At each completed epoch, gate scoring reuses the just-refreshed current L0
memory: no second CNN pass. Each active training case is scored jointly using
the complete eligible training support, excluding its own patient on recipient
and donor sides exactly as before. Query labels are used only after predicting
scores. Strict ties never count as wins or first-P Hit@1. RNG and module modes
are preserved. TRAIN gate/support preparation time is reported separately.

Promotion applies to the following epoch and resets the consecutive-pass count.
There is no timeout-based automatic promotion. The configured **40 epochs**
remain unchanged. If128 is not trained before epoch40, that incomplete exposure
is recorded; forty completed epochs do not imply full128 curriculum completion.
Reaching128, actual completed128-query epochs, and passing the final128 gate
are separate evidence fields. The final gate can never establish held-out
accuracy by itself.

## Evaluation, checkpoint and resources

All21 validation cases retain all P+128U from the original inventory, including
zero-P cases. BEST remains full-validation MRR, then observed micro R@1, then
negative pairwise loss. TRAIN curriculum Hit@1 is a **case** first-P metric; it
is not the same as observed micro R@1. A high score on sixteen candidates is not
reported as full128 quality.

The named new experiment has its own inventory, attempt directories, model,
optimizer, RNG, support, query cursor and stage/gate history. Resume validates
the exact source/config/data binding and replays the stored gate decisions.
The selected BEST's training stage is exported separately from the final
curriculum stage. Existing D and prior LocalCNN experiments are preserved.

The server launcher prints the physical GPU number and resolves the live GPU
selection using the existing selector. Defaults are physical GPU3, workers16,
CUDA40GiB, RSS192GiB, resident cache128GiB, input device cache8GiB, batch32,
support16 patients, one GPU, gradient accumulation1, effective batch32. The
existing actual-shape calibration measures admission and throughput before
training. A failed batch32 admission reports its error instead of inserting a
smaller production batch. No speed or accuracy gain is assumed in advance.

Per-update logs retain loss terms, module weight-change probes, gradient norm,
loader/transfer/forward/backward/optimizer/checkpoint times and memory. Progress
shows active U/128. At epoch end the terminal shows full128 validation followed
by TRAIN pair-win, Hit@1, margin, pass count and next-stage U count. Detailed
per-case gate outputs are stored as curriculum_epoch_NNN.json.

## Validation status

Unit scheduling/gate-state tests use explicitly labelled synthetic metadata;
they do not measure prediction quality. The separate actual-CT/CUDA verifier
uses the full unchanged neural model and real 128U per selected case, in an
explicit DEBUG inventory and separate output. It verifies actual gradients,
optimizer steps, full-candidate validation mechanics and exact pause/resume.
It starts from fresh seed42 weights and cannot prove ranking improvement.

The production84/21,40-epoch experiment must run on the server. No local DEBUG
result is promoted to production training or quality verification. The final
verification receipt and server command accompany the implementation delivery.

Completed local checks:40 UNIT tests, Python AST parsing and diff whitespace
checks passed. The actual RTX5070Ti/CT DEBUG run used four training cases
(548 full-bank rows,100 active query rows including all36 P and64 U) and one
held-out case with all P+128U. The full unchanged neural model completed five
updates at configured physical batch32. CNN/readout/L1/L2 module probes all
changed weights. Continuous versus paused/resumed model, optimizer, cursor/stage
state and RNG hashes matched exactly. Republishing a completed owned cursor in
a new directory performed no new updates and preserved those hashes.

Peak update allocation was2.499GiB; the actual batch32 calibration measured
33.91 rows/s and2.926GiB peak. A preceding preserved DEBUG calibration measured
batch16 at43.66 rows/s and batch32 at53.39 rows/s; those short measurements
do not establish server throughput. The first comparison chose different
calibrated batch sizes for continuous and paused arms, so it was rejected and
rerun with the same batch32. No failed comparison is reported as resume proof.

After the corrected fresh-weight DEBUG epoch the TRAIN pair-win was56.60%,
the mean margin was negative and the gate correctly stayed at16 U. This is
mechanical gate evidence only. It proves neither quality improvement nor
trained128-query quality. The full21 held-out production evaluation and the
40-epoch curriculum run have not been executed locally.
