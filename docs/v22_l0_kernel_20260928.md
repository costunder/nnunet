# L0 내부 계산·재계산 수정 및 실제 CT 짧은 CUDA 검증

2026-09-28. L0 실행 후보 구현·단위검사·실제 CT DEBUG 비교 완료. 전체 epoch 시간 단축, A100 MIG 검증, production 전환은 아직 완료되지 않았다. Basic CP와 실험 설계는 변경하지 않았다.

## 측정에서 확인한 비용

RTX5070Ti / torch2.8.0+cu128에서 기존 DEBUG cache의 inner_train 8개를 한 batch로 사용했다. 총 52,666 nodes / 2,761,602 edges, L0 4,718,420 parameters, 3층·128D·4heads, 원래 CNN·CT 해상도·그래프 전부 유지. CPU threads8 / loader workers4 / RAM available 약38.3GB / BF16 / edge workspace256MiB. production physical batch32를 변경한 것이 아니다.

기존 L0 한 forward/backward의 operator profiler에서 CNN encode forward는 19.67ms, 3개 graph block forward는 650.71ms였다. cudaLaunchKernel 호출35,842회, self CPU611.95ms였다. 작은 edge 연산·indexing·중간 tensor 초기화와 역전파가 반복됐다. 이는 **로컬 L0의 측정**이며 서버 3시간 중 정확한 몫을 측정한 것은 아니다. profiler 오버헤드, 중첩 timer 및 checkpoint early-stop을 포함하므로 항목들을 더해서 전체 시간으로 쓰지 않는다.

## 실제 수정

`tools/v22_l0_logit_stream.py`:

1. attribute-free L0 attention logit의 내부 checkpoint를 직접 backward 구현으로 교체했다. 필요한 node projection·COO·attention parameter를 저장하고 미분에 필요한 값만 다시 계산한다. 모든 edge×hidden activation을 보관하지 않는다.
2. edge feature 합·LeakyReLU·attention 곱과 backward의 대응 연산을 CUDA pointwise kernel로 합쳤다. 기존 PyTorch reduction 순서, BF16 cast 경계, chunk별 node gradient 누적은 유지했다.
3. aggregation에서 반복된 edge별 FP32 변환을 node별 한 번의 변환으로 옮겼다. edge 순서·chunk 경계·FP32 누적은 유지했다.
4. 인스턴스별 L0 forward namespace에만 새 aggregation을 연결했다. 모듈 전역 교체 없이 L1/L2는 기존 operator를 사용한다. context 종료·예외 시 원래 메서드를 복원한다.

CNN과 outer L0 checkpoint, dropout/RNG, full softmax, 모델·노드·edge·support·후보 수·batch·loss·optimizer 계약은 유지한다. CUDA kernel은 PyTorch에 포함된 jiterator/NVRTC로 컴파일하며 별도 시스템 설치는 없다. 내부 API의 서버 torch2.6.0+cu118 호환성은 아직 실측하지 않았다. 실패 시 숨기거나 다른 연산으로 fallback하지 않는다.

## 실제 CT 결과와 제한

동일 초기 weight/RNG/Adam에서 각 정책3update(첫1개 워밍업 제외)를 실행했다. 원본→후보→원본으로 반복해 원본의 시간 변동도 기록했다.

| 검사 | 원본 평균 | 수정 평균 | 관측 시간 감소 |
|---|---:|---:|---:|
| 첫 combined 비교 | 1.146665s | 1.019554s | 11.1% |
| L0 인스턴스에 한정한 최종본 | 1.209188s | 0.984409s | 18.6% |

측정 수가 적어 결과 범위는 약11~19%이며 장기 처리량 보장이 아니다. 각각 원본4개/후보2개의 워밍업 제외 update다. 첫 후보 update의 CUDA 컴파일 시간은 약3.4초로 워밍업에 포함된다. peak allocated는 1,013,252,096→1,015,488,000bytes(+2.13MiB)였다.

모든 후보3update에서 **출력·loss·전체 clipping 후 gradient·model·Adam·RNG가 bitwise 일치**했다. 최종12개 검사(9.175초)에는 수치미분, 빈 edge, 중복 edge, LeakyReLU zero 경계, FP32/BF16/FP64, multi-chunk/dropout, 예외 복원·L1/L2 격리가 포함된다.

실제 CT를 사용했지만 초기화된 full-size L0와 squared-output 진단 loss다. observed-rank/full support 학습이나 종양 성능 평가가 아니다. 같은 후보의 사전 profiler에서는 launch35,842→34,603회, logit forward 완료 호출105.24→63.27ms를 관측했다. 이 profiler는 scope 한정 전 L0 단독 실행이므로 성능 표와 독립된 진단이다.

남은 큰 비용은 scatter/indexing·gradient buffer·outer replay다. BF16 누적 순서와 dropout을 바꾸면서 이를 제거하면 동일한 학습이라는 보장이 깨질 수 있다. 이번 결과를 ‘3시간/epoch 해결’이나 ‘전체 최적화 완료’로 표시하지 않는다. validation/support refresh/저장 포함 epoch 비용은 미측정이다.
